# 1.1.4 La mise en place de l'intégration continue (CI)

## En bref

L'**intégration continue (CI)** sur Hublot, c'est le workflow GitHub **CI** (`.github/workflows/ci.yml`) : à chaque push ou pull request, la même chaîne s'exécute pour tout le monde — lint, 48 tests, audit npm production, build, E2E Playwright. Si un job échoue, le code n'est pas considéré comme prêt pour la production.

---

## Objectif pédagogique

Comprendre la **mise en place de l'intégration continue** : déclencheurs, étapes, critères de succès, et alignement avec le build Netlify.

---

## Contexte — projet Hublot

Le dépôt `Meriem1403/Hublot` reçoit des commits fréquents (données, UI, sécurité). Sans CI, chaque développeur pourrait pousser du code qui compile localement mais casse les tests ou introduit une vulnérabilité npm. La CI est la **porte de qualité commune** avant déploiement Netlify.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **CI (Continuous Integration)** | Intégration fréquente du code avec vérifications automatiques à chaque changement. |
| **Workflow** | Fichier YAML GitHub Actions décrivant jobs et étapes. |
| **Job** | Ensemble d'étapes exécutées sur une même machine virtuelle. |
| **Gate** | Condition bloquante (ex. CI verte) avant déploiement. |
| **Artefact** | Sortie du build (`build/`) prête à être publiée. |

---

## Ce qui a été mis en place

### Workflow principal : `ci.yml`

| Étape | Commande | Bloquant |
|-------|----------|----------|
| Installation | `npm ci` | Oui |
| Lint | `npm run lint` | Oui |
| Tests unitaires | `npm run test:run` (48 tests) | Oui |
| Audit production | `npm run audit:prod` | Oui |
| Build | `npm run build` | Oui |
| E2E | `npm run test:e2e` | Oui |

**Déclencheurs :** push et pull request sur `main` et `staging`.

### Workflows complémentaires

| Fichier | Rôle |
|---------|------|
| `codeql.yml` | Analyse statique sécurité (SAST) |
| `security-scan.yml` | Gitleaks + Trivy |
| `audit-scheduled.yml` | Audit npm hebdomadaire |

### Chaîne logique

```
git push / PR
  → GitHub Actions (CI)
  → lint → tests → audit → build → E2E
  → si vert : Netlify peut déployer (gate « required checks »)
```

---

## Pourquoi ces étapes

| Étape | Risque couvert |
|-------|----------------|
| ESLint | Erreurs de code, mauvaises pratiques |
| 48 tests Vitest | Régressions métier (filtres, calculs, sécurité session) |
| `audit:prod` | CVE dans les dépendances de production |
| Build | Artefact Netlify invalide |
| E2E | Parcours login / health cassé |

---

## Comment ça fonctionne

1. Le développeur pousse sur GitHub.
2. GitHub provisionne une VM Ubuntu éphémère.
3. Le workflow exécute les jobs dans l'ordre défini dans `ci.yml`.
4. En cas d'échec : notification GitHub, deploy Netlify bloqué si la gate est active.
5. En cas de succès : le commit est **intégrable** ; Netlify build le même `npm run build`.

### Alignement CI ↔ Netlify

| Étape | CI | Netlify |
|-------|-----|---------|
| Install | `npm ci` | `npm ci` |
| Tests | Oui | Non (déjà validé par CI) |
| Build | `npm run build` | `npm run build` |
| Publish | Vérifie `build/` | Publie `build/` |

---

## Quand

| Événement | CI |
|-----------|-----|
| Chaque push `main` / `staging` | Oui |
| Chaque pull request | Oui |
| Hebdomadaire | Audit planifié, CodeQL |
| Avant merge | DoD : CI verte |

---

## Preuves et démonstration

```bash
# Reproduire localement la CI
npm run lint
npm run test:run
npm run audit:prod
npm run build
npm run test:e2e
```

Interface : [github.com/Meriem1403/Hublot/actions](https://github.com/Meriem1403/Hublot/actions) → workflow **CI**.

---

## Synthèse

> « La CI Hublot est le fichier **`ci.yml`** : cinq contrôles bloquants sur chaque push. Elle garantit que le dossier **`build/`** déployé par Netlify correspond à du code **testé, audité et compilé**. »
