# 1.1.5 La mise en place de la livraison ou déploiement continu (CD)

## En bref

La **livraison continue (CD)** publie automatiquement une version validée par la CI. Sur Hublot, la **CD cloud** passe par **Netlify** (webhook Git + gate sur le workflow CI) ; la **CD NAS** reste **semi-automatique** via `deploy-nas.sh` et le workflow `cd-nas.yml`.

---

## Objectif pédagogique

Comprendre la **mise en place du déploiement continu** : séparation CI/CD, canaux de publication, et conditions de mise en production.

---

## Contexte — projet Hublot

Après une CI verte sur `main`, les agents DIRM doivent accéder à la nouvelle version sur **https://dirmhublot.netlify.app** sans intervention manuelle. En parallèle, une copie **on-premise** sur Synology peut être nécessaire ; elle suit un processus distinct pour des raisons de secrets SSH et de réseau.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **CD (Continuous Delivery/Deployment)** | Publication automatisée d'une version vers un environnement cible. |
| **Build hook** | URL Netlify déclenchant un rebuild (workflow `cd-netlify.yml`, optionnel). |
| **Required check** | Netlify n'affiche en prod que si le workflow **CI** GitHub est vert. |
| **Deploy Preview** | URL temporaire pour une branche ou une PR. |
| **Rollback** | Retour à un déploiement Netlify ou commit Git antérieur. |

---

## Ce qui a été mis en place

### CD Netlify (principal)

| Élément | Détail |
|---------|--------|
| Déclencheur | Push Git (branche connectée, en pratique `main`) |
| Config | `netlify.toml` — `npm run build`, publish `build/` |
| Gate | *Deploy only when required checks pass* → check **CI** |
| URL prod | https://dirmhublot.netlify.app |
| Staging | Branche `staging` + deploy previews (voir 1.2.3) |

### CD NAS (complément)

| Élément | Détail |
|---------|--------|
| Script | `scripts/deploy-nas.sh` (build, tests, rsync optionnel) |
| Workflow | `.github/workflows/cd-nas.yml` (`workflow_dispatch` + secrets SSH) |
| Runtime | Docker + Nginx sur le Synology (`docker-compose.yml`) |

### Workflows associés

| Fichier | Rôle |
|---------|------|
| `ci.yml` | Qualité **avant** toute publication |
| `cd-netlify.yml` | Hook optionnel post-CI |
| `cd-nas.yml` | Déploiement SSH optionnel |

---

## Pourquoi CI et CD séparés

| Décision | Raison |
|----------|--------|
| GitHub Actions ne déploie pas directement | Netlify gère HTTPS, CDN, variables d'env, rollbacks UI |
| Gate sur CI | Évite un deploy Netlify sur un commit cassé |
| NAS manuel / semi-auto | Secrets et réseau interne non exposés dans la CI standard |

---

## Comment ça fonctionne

### Flux cloud (happy path)

1. Merge sur `main` avec **CI verte**.
2. Netlify reçoit le webhook, exécute `npm run build`.
3. Publication du dossier `build/` + en-têtes de sécurité (`netlify.toml`).
4. Vérification : `curl https://dirmhublot.netlify.app/health.json`

### Flux NAS

1. `npm run build` (ou CI déjà passée).
2. `./scripts/deploy-nas.sh` ou workflow **CD NAS Synology** avec secrets configurés.
3. Redémarrage du conteneur sur le NAS.

### Rollback Netlify

Dashboard Netlify → **Deploys** → sélectionner un deploy précédent → **Publish deploy**.

---

## Quand

| Événement | CD Netlify | CD NAS |
|-----------|------------|--------|
| Push `main` + CI OK | Auto | — |
| Push `staging` | Preview / staging | — |
| Manuel équipe | — | `deploy-nas.sh` ou workflow dispatch |
| Incident prod | Rollback deploy | Restauration fichiers + restart |

---

## Preuves et démonstration

- Netlify : [app.netlify.com](https://app.netlify.com) → site → **Deploys**
- GitHub : Actions → **CI** (prérequis) puis éventuellement **CD Netlify**
- Headers prod : `npm run security:headers`

---

## Synthèse

> « La CD Hublot, c'est **Netlify après CI verte** pour le cloud, et un **script NAS** pour l'interne. La CI dit *si* on peut livrer ; la CD dit *où* la version est publiée. »
