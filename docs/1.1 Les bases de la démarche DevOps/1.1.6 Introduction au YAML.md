# 1.1.6 Introduction au YAML

## En bref

Le **YAML** est le format utilisé pour décrire la **CI** (GitHub Actions), la **CD** (`netlify.toml`), et l'**infrastructure as code** du projet. Sur Hublot, comprendre YAML, c'est lire `ci.yml` et `netlify.toml` : déclencheurs, jobs, commandes, variables et en-têtes HTTP.

---

## Objectif pédagogique

Comprendre les **bases du YAML** appliquées au déploiement : structure, indentation, listes, et lecture des fichiers de configuration du projet.

---

## Contexte — projet Hublot

Les pipelines ne sont pas configurés uniquement dans une interface graphique : ils sont **versionnés dans Git**. Modifier la CI ou le déploiement Netlify, c'est éditer un fichier YAML, ouvrir une PR, et valider que la CI reste verte.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **YAML** | Format de sérialisation lisible par humain (indentation significative). |
| **Clé / valeur** | `command: npm run build` |
| **Liste** | Éléments préfixés par `-` |
| **Bloc** | Section indentée (job, step, header Netlify) |
| **Workflow** | Fichier `.github/workflows/*.yml` exécuté par GitHub Actions |

---

## Ce qui a été mis en place

| Fichier | Rôle |
|---------|------|
| `.github/workflows/ci.yml` | Pipeline CI (lint, tests, audit, build, E2E) |
| `.github/workflows/cd-netlify.yml` | Hook Netlify optionnel |
| `.github/workflows/cd-nas.yml` | Déploiement NAS optionnel |
| `.github/workflows/codeql.yml` | SAST |
| `.github/workflows/security-scan.yml` | Gitleaks, Trivy |
| `netlify.toml` | Build, publish, contexts, headers, redirects SPA |
| `docker-compose.*.yml` | Services Docker |

---

## Pourquoi YAML (et pas seulement des clics UI)

| Intérêt | Exemple Hublot |
|---------|----------------|
| Traçabilité | Chaque changement de pipeline a un commit |
| Reproductibilité | Même fichier sur tous les clones |
| Revue de code | PR sur `ci.yml` comme sur le code applicatif |
| Documentation vivante | Le fichier **est** la procédure |

---

## Comment ça fonctionne

### Exemple CI — déclencheurs (`ci.yml`)

```yaml
name: CI
on:
  push:
    branches: [main, staging]
  pull_request:
    branches: [main, staging]
```

**Lecture :** à chaque push ou PR sur `main`/`staging`, le workflow **CI** démarre.

### Exemple CI — un job

```yaml
jobs:
  unit-tests:
    name: Tests unitaires
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:run
```

**Lecture :** job nommé *Tests unitaires*, machine Ubuntu, étapes checkout → install → tests.

### Exemple Netlify (`netlify.toml`)

```toml
[build]
  command = "npm run build"
  publish   = "build"

[[headers]]
  for = "/*"
  [headers.values]
    X-Frame-Options = "DENY"
```

**Lecture :** build Vite, publication `build/`, en-têtes de sécurité sur toutes les routes.

> Note : `netlify.toml` utilise la syntaxe **TOML** (très proche du YAML par l'indentation et les sections). Le référentiel Studi regroupe souvent YAML/TOML sous « configuration déclarative ».

---

## Quand modifier ces fichiers

| Besoin | Fichier |
|--------|---------|
| Ajouter une étape CI (ex. nouveau script npm) | `ci.yml` |
| Changer Node version | `ci.yml` + `netlify.toml` `[build.environment]` |
| Nouveau header HTTP | `netlify.toml` `[[headers]]` |
| Nouveau workflow sécurité | `.github/workflows/*.yml` |

---

## Preuves et démonstration

```bash
# Valider la syntaxe (lecture humaine + PR)
cat .github/workflows/ci.yml
cat netlify.toml
# Après modification : push → onglet Actions → workflow CI
```

## Synthèse

> « Sur Hublot, le YAML (et le TOML Netlify) **décrit la CI et la CD** : qui déclenche quoi, quelles commandes `npm` exécuter, où publier `build/`, quels headers appliquer. Savoir lire ces fichiers, c'est savoir **comment le déploiement sécurisé est automatisé**. »
