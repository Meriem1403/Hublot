# 1.2.3 Mettre en place un environnement de test

## En bref

Hublot s'exécute à **quatre niveaux** : développement local, CI GitHub, staging Netlify et production. Ce chapitre décrit comment nous avons configuré la **branche `staging`**, les **Deploy Previews** et les variables d'environnement pour tester sans impacter `dirmhublot.netlify.app`. Il complète les fondamentaux du [1.1.3](../1.1%20Les%20bases%20de%20la%20d%C3%A9marche%20DevOps/1.1.3%20Les%20bases%20d%27un%20environnement%20de%20test.md).

---

## Objectif pédagogique

Mettre en place un **environnement de test** (préproduction) distinct de la production : isolation, configuration, promotion vers la prod.

---

## Contexte — projet Hublot

Les tests unitaires tournent en local et en CI sans navigateur métier complet. Les scénarios ST-F* (auth, filtres, données réelles) nécessitent une URL déployée avec identifiants de test. Le staging évite de valider une release directement sur la production DIRM.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **DEV** | Poste développeur — `npm run dev`, port 5173. |
| **TEST (CI)** | Machine éphémère GitHub Actions — workflow **CI**. |
| **STAGING** | Préproduction Netlify — branche `staging` ou Deploy Preview. |
| **PROD** | Site public — `https://dirmhublot.netlify.app`. |
| **Branch deploy** | Déploiement Netlify lié à une branche Git nommée. |
| **Deploy Preview** | URL temporaire générée pour chaque pull request. |

---

## Ce qui a été mis en place

Nous avons défini quatre contextes d'exécution et aligné la configuration Netlify.

| Niveau | Où | URL type |
|--------|-----|----------|
| **DEV** | `npm run dev` | `http://localhost:5173` |
| **TEST** | GitHub Actions — workflow **CI** | Onglet Actions du dépôt |
| **STAGING** | Branche `staging` ou preview PR | `staging--dirmhublot.netlify.app` ou `deploy-preview-NN--…` |
| **PROD** | Branche `main` | `https://dirmhublot.netlify.app` |

Le fichier `netlify.toml` définit `VITE_APP_ENV = "staging"` pour le contexte staging. La CI s'exécute sur `main` et `staging` avec les mêmes jobs (lint, 48 tests, audit, build, E2E).

---

## Pourquoi ces choix

Un même test n'a pas le même sens selon l'environnement : les unitaires bloquent en CI ; l'auth manuelle utilise des comptes staging ; les headers HTTPS se vérifient en prod après déploiement. Nous séparons les secrets (variables Netlify par contexte) pour limiter les tests accidentels sur la prod. Les Deploy Previews permettent une démo jury sans merge.

| Test | DEV | CI | STAGING | PROD |
|------|-----|-----|---------|------|
| Unitaires | Local | Bloquant | — | — |
| E2E | Local / preview | Bloquant | Recommandé | — |
| Auth manuelle | `.env` local | — | Comptes staging | Comptes prod |
| Headers HTTPS | — | — | curl staging | curl prod |

---

## Comment ça fonctionne

### Branche `staging` sur Netlify

```bash
git checkout -b staging
git push -u origin staging
```

Sur Netlify : **Site configuration** → **Build & deploy** → **Branches and deploy contexts** → activer **Branch deploys** pour `staging`.

Variables d'environnement (contexte staging) : `VITE_APP_USERNAME`, `VITE_APP_PASSWORD` (comptes de test, distincts de la prod si possible) ; `VITE_SENTRY_DSN` optionnel.

### Deploy Previews (pull requests)

Pour chaque PR vers `main` : activer **Deploy Previews** sur Netlify. URL du type `deploy-preview-NN--dirmhublot.netlify.app` avec `VITE_APP_ENV=preview` (défini dans `netlify.toml`).

### Promotion staging → production

1. Merge `staging` → `main` (ou PR directe avec CI verte).
2. CI verte sur `main`.
3. Netlify déploie la production après les required checks.

### Checklist activation staging

- [ ] Branche `staging` poussée sur GitHub
- [ ] Branch deploys activés sur Netlify
- [ ] Variables d'env staging configurées
- [ ] CI verte sur `staging`
- [ ] URL staging testée (login + un onglet)

> **Note :** l'URL `staging--dirmhublot.netlify.app` peut renvoyer 404 tant que les branch deploys ne sont pas activés ; la campagne documentée en [1.2.9](./1.2.9%20Rapport%20d%27ex%C3%A9cution%20des%20tests.md) utilise alors la QA locale (`build:e2e`).

---

## Quand

| Moment | Environnement |
|--------|---------------|
| Codage quotidien | DEV |
| Chaque push / PR | CI (TEST) |
| Validation avant merge sensible | STAGING ou Deploy Preview |
| Contrôles post-livraison | PROD (lecture seule, headers) |

---

## Preuves et démonstration

```bash
npm run check:env          # lint + tests + audit + build en local
npm run build:e2e          # artefact QA (e2e-user / e2e-pass)
npm run preview:test       # http://127.0.0.1:4173
```

| Vérification | Commande / accès |
|--------------|------------------|
| CI sur `staging` | GitHub Actions → workflow **CI** |
| Preview PR | Netlify → Deploy Preview de la PR |
| Prod | Navigateur → `https://dirmhublot.netlify.app` |

---

## Synthèse

L'environnement de test Hublot sépare DEV, CI, staging Netlify et production : même pipeline de qualité sur `main` et `staging`, URLs de préproduction pour les scénarios manuels, promotion contrôlée vers `dirmhublot.netlify.app`.
