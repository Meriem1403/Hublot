# 1.2.4 Les outils et les stratégies des tests de sécurité

## En bref

Les tests de sécurité de Hublot cherchent les failles **avant** la production : données RH, accès au tableau de bord, dépendances npm, secrets Git, en-têtes HTTP. Nous appliquons le **shift-left** (dès la CI) et la **défense en profondeur** (plusieurs familles d'outils). Ce chapitre recense outils, commandes et scénarios ST-SEC* du dépôt `Meriem1403/Hublot`.

---

## Objectif pédagogique

Identifier les **outils et stratégies des tests de sécurité** pour un déploiement sécurisé : SCA, SAST, scan de secrets, tests unitaires de garde-fous, contrôle de configuration.

---

## Contexte — projet Hublot

L'application traite des effectifs nominatifs (RGPD). Un tableau de bord accessible sans habilitation, une CVE dans une librairie ou un mot de passe commité exposent l'institution. La production `dirmhublot.netlify.app` doit être durcie par des contrôles reproductibles à chaque push.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Shift-left** | Tester la sécurité tôt (commit, CI), pas seulement avant la prod. |
| **Défense en profondeur** | Plusieurs couches complémentaires (aucun outil ne suffit seul). |
| **SCA** | Analyse des dépendances (CVE connues). |
| **SAST** | Analyse statique du code source sans exécution. |
| **DAST** | Test de l'application en cours d'exécution (non déployé sur Hublot). |
| **Secret scanning** | Détection de mots de passe ou clés dans Git. |
| **Bloquant** | Étape CI qui empêche la livraison si échec. |

---

## Ce qui a été mis en place

Nous croisons six familles de contrôles intégrés au dépôt et à GitHub Actions.

| Outil | Famille | Rôle | Intégration |
|-------|---------|------|-------------|
| `npm audit` / `audit:prod` | SCA | CVE prod — critical bloquant, high via allowlist | `ci.yml` + `audit-scheduled.yml` |
| **Dependabot** | SCA préventif | PR de mise à jour npm / Actions | `.github/dependabot.yml` |
| **Trivy** | SCA | Scan complémentaire filesystem | `security-scan.yml` (informatif) |
| **CodeQL** | SAST | Motifs dangereux JS/TS | `codeql.yml` |
| **Gitleaks** | Secrets | Scan arborescence | `security-scan.yml` (**bloquant**) |
| **Vitest** `security.test.ts` | Unitaire | Sanitization, filtres, session, masquage RH | CI via `test:run` |
| **`check-security-headers.sh`** | Configuration | HTTPS + en-têtes (ST-SEC01) | `npm run security:headers` |
| **Playwright** | E2E accès | Login refusé / session | CI `test:e2e` |
| **ESLint** | Qualité préventive | Réduction de motifs à risque | CI `lint` |

**Principe :** ce qui est certain et maîtrisé **bloque** (audit prod, Gitleaks) ; Trivy et CodeQL **informent** dans l'onglet Security pour triage.

---

## Pourquoi ces choix

Une seule barrière (ex. uniquement `npm audit`) laisserait passer des secrets commités ou des failles de logique applicative. Les tests unitaires sur `src/utils/security.ts` valident les garde-fous métier (filtres, XSS) à chaque commit, plus vite qu'un pentest. Les en-têtes Netlify compensent l'absence de nginx en prod SaaS ; le fichier `nginx.conf` reste la référence pour déploiement NAS.

| Enjeu | Risque | Réponse |
|-------|--------|---------|
| Données RH | Fuite RGPD | Masquage + auth + pas de JSON dans Git |
| Accès dashboard | Consultation non habilitée | Auth + Playwright ST-F01 |
| Chaîne npm | CVE embarquée | `audit:prod`, Dependabot |
| Secrets | Commit accidentel | Gitleaks, `.gitignore` |
| Configuration HTTP | Clickjacking, MIME sniffing | ST-SEC01, `netlify.toml` |

---

## Comment ça fonctionne

### En local

```bash
npm run security:test      # ST-SEC02 — 15 tests
npm run audit:prod         # ST-SEC04
npm run security:headers   # ST-SEC01 — prod par défaut
npm run security:headers https://staging--dirmhublot.netlify.app
```

### En CI (GitHub Actions)

| Workflow | Déclenchement | Contenu sécurité |
|----------|---------------|------------------|
| `ci.yml` | push / PR `main`, `staging` | lint, **48 tests** (dont sécurité), **audit bloquant**, build, E2E |
| `codeql.yml` | push / PR + hebdo | SAST |
| `security-scan.yml` | push / PR + hebdo | Gitleaks (bloquant) + Trivy |
| `audit-scheduled.yml` | hebdomadaire | audit npm + artefact |

Détail déploiement : [1.2.4.2](./1.2.4.2%20S%C3%A9curit%C3%A9%20du%20d%C3%A9ploiement.md). Audit : [1.2.4.3](./1.2.4.3%20Audit%20des%20d%C3%A9pendances.md). Applicatif : [1.2.4.1](./1.2.4.1%20Mesures%20de%20s%C3%A9curit%C3%A9%20applicative.md).

## Preuves et démonstration

### Ordre conseillé pour une démonstration

| # | Commande | Scénario |
|---|----------|----------|
| 1 | `npm run security:test` | ST-SEC02 |
| 2 | `npm run audit:prod` | ST-SEC04 |
| 3 | `npm run security:headers` | ST-SEC01 |
| 4 | `npm run test:run` | ST-AUTO / ST-SEC02 (48 tests) |
| 5 | `npm run lint` | ST-AUTO-01 |

```bash
npm run security:test
npm run audit:prod
npm run security:headers
```

Sur GitHub : **Actions** (CI, CodeQL, Scans sécurité) ; **Security** → Code scanning, Dependabot.

### Couverture par scénarios

| Scénario | Intention | Outil |
|----------|-----------|-------|
| ST-SEC01 | En-têtes HTTP prod | `security:headers` / curl |
| ST-SEC02 | Garde-fous applicatifs | `security.test.ts` |
| ST-SEC03 | Pas de secret commité | Gitleaks |
| ST-SEC04 | Dépendances prod | `audit:prod` + Trivy |
| ST-SEC05 | Failles code | CodeQL |
| ST-F01 | Accès refusé | Playwright |

Détail des scénarios : [1.2.2](./1.2.2%20Elaborer%20un%20sc%C3%A9nario%20de%20test.md).

### Correspondance OWASP (repère)

| Catégorie OWASP | Couverture Hublot |
|-----------------|-------------------|
| A01 Broken Access Control | Auth + E2E login |
| A02 Cryptographic Failures | HTTPS/TLS Netlify, HSTS |
| A03 Injection / XSS | `sanitizeInput` + Vitest + CodeQL |
| A05 Security Misconfiguration | En-têtes + ST-SEC01 |
| A06 Vulnerable Components | `audit:prod`, Dependabot, Trivy |
| A07 Auth Failures | Session + expiration (tests) |
| Secrets exposure | Gitleaks + variables Netlify |

### Limites et évolutions

| Constat | Évolution |
|---------|-----------|
| CSP absente sur Netlify (HSTS + X-Frame + nosniff présents) | Aligner `netlify.toml` sur `nginx.conf` |
| Auth côté client (`VITE_*`) | JWT / SSO serveur |
| Pas de DAST | OWASP ZAP baseline sur staging |
| CORS `*` fonction Neon | Restreindre à l'origine front |
| Trivy informatif | Bloquant après triage |

### Glossaire outils et menaces (référence)

| Sigle / terme | En clair |
|---------------|----------|
| **CVE** | Identifiant public d'une vulnérabilité connue |
| **XSS** | Injection de script dans une page |
| **Sanitization** | Nettoyage des entrées utilisateur |
| **HSTS** | Force HTTPS |
| **CSP** | Restreint les sources de scripts (XSS) |
| **X-Frame-Options** | Anti-clickjacking |
| **nosniff** | Anti MIME-sniffing |
| **SARIF** | Format des alertes dans l'onglet Security GitHub |

---

## Synthèse

La sécurité Hublot combine shift-left et défense en profondeur : à chaque intégration, SCA, SAST, scan de secrets, tests Vitest et E2E d'accès ; après déploiement, contrôle des en-têtes HTTP. Le bloquant arrête la livraison ; le reste alimente la revue dans GitHub Security.
