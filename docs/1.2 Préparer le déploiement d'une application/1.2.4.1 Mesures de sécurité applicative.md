# 1.2.4.1 Mesures de sécurité applicative

## En bref

La sécurité **applicative** de Hublot protège les données RH dans le navigateur : authentification avant le tableau de bord, sanitization des entrées, masquage des champs sensibles, session limitée dans le temps. Ces mesures sont codées dans `src/utils/security.ts` et `AuthGuard`, et vérifiées par **15 tests Vitest** inclus dans les **48 tests** de la CI.

---

## Objectif pédagogique

Décrire les **mesures de sécurité applicative** : authentification, validation, protection des données affichées, session.

---

## Contexte — projet Hublot

Hublot est une SPA React déployée en statique sur Netlify. L'accès métier (filtres région/service, graphiques effectifs) n'est pas public : seuls les agents DIRM habilités doivent consulter les agrégations. Les identifiants sont injectés au build via variables `VITE_*` ; la session vit dans `sessionStorage`.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **AuthGuard** | Composant qui bloque le tableau de bord sans authentification. |
| **Sanitization** | Nettoyage des entrées (`sanitizeInput`) contre XSS. |
| **validateFilter** | Refus des valeurs de filtre hors liste autorisée. |
| **Masquage RH** | Fonctions `maskName`, `maskId`, `maskDateOfBirth`. |
| **Session** | État connecté avec expiration (8 h). |

---

## Ce qui a été mis en place

### Authentification et autorisation

- **Page de connexion** avant tout accès au tableau de bord.
- **AuthGuard** : vérification au chargement des routes protégées.
- **Session** : `sessionStorage`, expiration testée (8 heures).
- **Identifiants** : `VITE_APP_USERNAME` / `VITE_APP_PASSWORD` (Netlify ou `.env` local, jamais dans Git).

Évolution documentée : auth serveur (JWT / SSO) pour renforcer le modèle actuel côté client.

### Validation et sanitization

- `sanitizeInput()` : neutralise balises HTML, `javascript:`, handlers d'événements.
- `validateFilter()` : n'accepte que les valeurs de filtre attendues (région, service, etc.).

### Protection des données sensibles

Dans `src/utils/security.ts` :

| Fonction | Rôle |
|----------|------|
| `maskName()` | Masque noms / prénoms |
| `maskId()` | Masque identifiants |
| `maskDateOfBirth()` | N'affiche que l'année de naissance |

Les fichiers `agents.json` et exports Excel sont **hors dépôt** (`.gitignore`).

### Déploiement NAS (complément)

Le fichier `nginx.conf` prévoit HTTP Basic, rate limiting, blocage d'accès direct aux `.json`, headers CSP/HSTS — référence pour hébergement Synology, distinct de Netlify prod.

---

## Pourquoi ces choix

Les données RH imposent le **masquage** et l'**auth** même en environnement interne. La sanitization limite le XSS si une entrée utilisateur est réinjectée dans le DOM. Les tests unitaires verrouillent ces comportements à chaque commit, plus fiable qu'une revue manuelle répétée. L'auth par variables de build est un compromis Studi (SPA statique) avec trajectoire JWT documentée.

---

## Comment ça fonctionne

1. L'utilisateur ouvre `dirmhublot.netlify.app` → écran login.
2. Soumission du formulaire → comparaison avec `import.meta.env.VITE_APP_*`.
3. Succès → écriture session + affichage du tableau de bord sous **AuthGuard**.
4. Filtres et exports passent par `validateFilter` / `sanitizeInput` selon le flux.
5. Affichage nominatif limité via fonctions de masquage quand activé.

Fichiers clés : `src/utils/security.ts`, `src/utils/security.test.ts`, composants d'authentification du front.

## Quand

| Moment | Contrôle applicatif |
|--------|---------------------|
| Chaque `npm run test:run` / CI | 15 tests `security.test.ts` + autres unitaires |
| Avant démo | `npm run security:test` |
| Revue de code | Vérifier qu'aucun secret n'entre dans le bundle |
| Évolution auth | Rejouer ST-F01 et E2E |
