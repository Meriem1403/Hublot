# 1.2.4.3 Audit des dépendances

## En bref

L'**audit npm** vérifie que les librairies embarquées en production n'introduisent pas de CVE critiques non maîtrisées. Sur Hublot, `npm run audit:prod` est **bloquant** en CI ; une allowlist documente les exceptions assumées. Un audit hebdomadaire complète le contrôle à chaque push.

---

## Objectif pédagogique

Mettre en place l'**audit des dépendances** : commandes, règles CI, allowlist et actions correctives.

---

## Contexte — projet Hublot

Le site Netlify sert uniquement le bundle statique `build/` : seules les dépendances **production** comptent pour le risque exposé aux utilisateurs. Les outils de dev (Vitest, ESLint) peuvent avoir des alertes sans impacter la prod — d'où la commande filtrée `audit:prod`.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **SCA** | Analyse des composants tiers (npm). |
| **CVE** | Identifiant public d'une vulnérabilité. |
| **audit:prod** | Script `scripts/npm-audit-prod.sh` — `--omit=dev`. |
| **Allowlist** | Liste blanche des CVE ou packages acceptés temporairement. |
| **Critical / High** | Niveaux de sévérité npm audit. |

---

## Ce qui a été mis en place

| Commande | Usage |
|----------|--------|
| `npm run audit:prod` | Audit **production** — utilisé en CI |
| `npm audit` | Rapport complet (dev inclus) — diagnostic local |

### Règles CI

1. **Critical** sur dépendances prod → **bloquant**, sans exception.
2. **High** sur dépendances prod → bloquant sauf packages dans `security/audit-allowlist.json`.
3. Rapport hebdomadaire : workflow **Audit npm planifié** (lundi 6h UTC).

### Allowlist actuelle

| Package | Motif |
|---------|--------|
| `react-simple-maps` (+ chaîne d3) | Cartographie ; correctif = downgrade majeur ; usage client interne |

Fichier : `security/audit-allowlist.json` — toute nouvelle entrée exige motif métier et date de revue en PR.

Scénario lié : **ST-SEC04** ([1.2.2](./1.2.2%20Elaborer%20un%20sc%C3%A9nario%20de%20test.md)).

---

## Pourquoi ces choix

Bloquer sur *critical* protège sans paralyser le projet sur des alertes dev. L'allowlist évite les faux blocages documentés (cartographie) tout en forçant une revue périodique. Dependabot et Trivy complètent la prévention — voir [1.2.4](./1.2.4%20Les%20outils%20et%20les%20strat%C3%A9gies%20des%20tests%20de%20s%C3%A9curit%C3%A9.md).

---

## Comment ça fonctionne

1. La CI exécute `npm run audit:prod` après les tests unitaires.
2. Le script filtre les vulnérabilités selon sévérité et allowlist.
3. Exit code non nul → job rouge → pas de merge recommandé.
4. En local, après correctif : `npm audit fix` puis `npm run audit:prod`.

```bash
npm audit fix              # correctifs sans breaking change
npm audit fix --force      # uniquement après revue (risque régression)
npm run audit:prod         # re-vérification
```

---

## Quand

| Moment | Action |
|--------|--------|
| Chaque push / PR | `audit:prod` en CI |
| Hebdomadaire | `audit-scheduled.yml` |
| Après mise à jour npm | Relancer `audit:prod` localement |
| Revue allowlist | À chaque changement de dépendance carto |

---

## Preuves et démonstration

```bash
npm run audit:prod
# Attendu : exit 0 en l'état du dépôt validé
```

| Preuve | Où |
|--------|-----|
| Job **Audit npm** vert | GitHub Actions → workflow **CI** |
| Artefact hebdo | Workflow audit planifié |
| Allowlist versionnée | `security/audit-allowlist.json` |

---

## Synthèse

L'audit des dépendances Hublot bloque les CVE critical en production et encadre les high via allowlist documentée, exécuté à chaque CI sur `Meriem1403/Hublot`.
