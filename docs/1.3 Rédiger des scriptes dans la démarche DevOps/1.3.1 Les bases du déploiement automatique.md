# 1.3.1 Les bases du déploiement automatique

## En bref

Ce chapitre pose les fondations du **déploiement automatique** pour Hublot : scripts reproductibles, séparation CI (qualité) et CD (publication), deux cibles (Netlify cloud et NAS Synology interne). Nous avons choisi des scripts Bash idempotents et des workflows GitHub Actions plutôt qu'une exécution manuelle à chaque livraison. Le dépôt `Meriem1403/Hublot` et la production `https://dirmhublot.netlify.app` servent de référence concrète.

---

## Objectif pédagogique

**Comprendre les bases du déploiement automatique** : scripts exécutables en local et en pipeline, chaîne build → artefacts → publication, traçabilité et reproductibilité dans une démarche DevOps.

---

## Contexte — projet Hublot

Hublot est le tableau de bord RH de la DIRM Méditerranée (effectifs, filtres région/service, indicateurs ETP). Chaque mise en production doit livrer une SPA React compilée et, le cas échéant, des données `agents.json` cohérentes. L'équipe ne peut pas se permettre un déploiement « à la main » sans tests : les **48 tests Vitest** et le workflow **CI** (`.github/workflows/ci.yml`) bloquent les régressions avant publication sur Netlify ou copie vers le NAS.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Déploiement automatique** | Publication déclenchée par un script ou un pipeline, avec les mêmes étapes à chaque fois. |
| **Script idempotent** | Relançable sans effet de bord imprévisible (même entrée → même sortie). |
| **Artefact** | Dossier `build/` produit par `npm run build`, servi par Netlify ou Nginx. |
| **CI** | Intégration continue : lint, tests, audit, build — sans déployer. |
| **CD** | Livraison continue : Netlify (`cd-netlify.yml`) ou NAS (`deploy-nas.sh`, `cd-nas.yml`). |

---

## Ce qui a été mis en place

Nous avons structuré le déploiement en **trois couches** :

1. **Qualité automatisée** — workflow GitHub **CI** : ESLint, `npm run test:run` (48 tests), `npm run audit:prod`, build Vite, tests Playwright E2E.
2. **CD cloud** — Netlify relie le dépôt `main` : build `npm run build`, publication du dossier `build/` vers `https://dirmhublot.netlify.app` (détail dans [1.1.5](../1.1%20Les%20bases%20de%20la%20d%C3%A9marche%20DevOps/1.1.5%20La%20mise%20en%20place%20de%20la%20livraison%20ou%20d%C3%A9ploiement%20continu%20(CD).md)).
3. **CD interne** — script `scripts/deploy-nas.sh` : build local contrôlé, copie `build/` et `dist/`, rsync SSH optionnel vers un Synology.

Les scripts vivent dans `scripts/` ; la documentation opérationnelle est dans `scripts/README.md` et [1.2.7](../1.2%20Pr%C3%A9parer%20le%20d%C3%A9ploiement%20d%27une%20application/1.2.7%20Documenter%20le%20processus%20de%20d%C3%A9ploiement.md).

---

## Pourquoi ces choix

**Séparer CI et CD** évite de déployer une version qui n'a pas passé les tests : Netlify peut attendre les required checks GitHub. **Script NAS dédié** répond à la contrainte réseau interne (pas de build `npm ci` lourd sur le Synology) : le poste de dev ou la CI prépare `build/`, le NAS sert les fichiers statiques via `docker-compose.yml` et Nginx. Nous avons écarté un déploiement FTP manuel (non traçable, sans gate qualité). Docker multi-étapes sur le NAS reste disponible (`docker-compose.prod.yml`) mais la voie recommandée est build hors NAS puis montage statique.

---

## Comment ça fonctionne

### Chaîne globale

```
Développeur → git push (main / staging)
  → GitHub Actions CI (ci.yml) : lint → 48 tests → audit → build → E2E
  → CD Netlify (si main + checks verts) → dirmhublot.netlify.app
  → ou ./scripts/deploy-nas.sh [--rsync] → NAS :8080
```

### Rôle de `deploy-nas.sh` (aperçu)

Le script enchaîne `npm ci`, `npm run lint`, `npm run test:run`, `npm run build`, vérifie `build/index.html`, synchronise vers `dist/` pour compatibilité compose, puis optionnellement rsync vers `NAS_HOST` / `NAS_PATH`. Le détail d'écriture et d'usage est dans [1.3.2](./1.3.2%20R%C3%A9diger%20et%20utiliser%20un%20script%20de%20d%C3%A9ploiement.md).

### Données et application

Les données RH proviennent d'exports Excel RenoiRH ; la chaîne d'évolution (`run-evolution-pipeline.sh`, `convert_suivi_etpt_to_json.py`) alimente `public/data/agents.json` avant commit ou push Neon — voir chapitres [1.3.3](./1.3.3%20Les%20bases%20des%20scripts%20d%27%C3%A9volution.md) à [1.3.5](./1.3.5%20Optimiser%20les%20scripts%20d%27%C3%A9volution.md).

## Quand

| Moment | Action automatisée |
|--------|-------------------|
| Chaque push / PR sur `main` ou `staging` | Workflow **CI** complet |
| Merge sur `main` (checks verts) | Déploiement Netlify |
| Besoin réseau interne DIRM | `deploy-nas.sh` (manuel ou `cd-nas.yml`) |
| Mise à jour mensuelle des effectifs | Pipeline d'évolution puis commit / push données |
| Démonstration de validation | Rejouer CI + URL prod + éventuellement NAS |

---

## Preuves et démonstration

Après un push sur `main`, vérifier que le workflow **CI** est vert sur [GitHub Actions — Meriem1403/Hublot](https://github.com/Meriem1403/Hublot/actions/workflows/ci.yml).

```bash
# Reproduire localement la gate qualité du déploiement
npm ci
npm run lint
npm run test:run    # attendu : 48 tests passés
npm run build
test -f build/index.html
```

Pour le NAS, sans rsync :

```bash
./scripts/deploy-nas.sh
# Artefacts prêts : build/ et dist/
```

| Élément | Valeur attendue |
|---------|-----------------|
| Tests unitaires | 48 passed (Vitest) |
| Prod cloud | `https://dirmhublot.netlify.app` |
| Workflow CI | `.github/workflows/ci.yml` |

---

## Synthèse

Le déploiement automatique de Hublot repose sur la CI GitHub (qualité), la CD Netlify (prod publique) et le script `deploy-nas.sh` (réseau interne), tous reproductibles et alignés sur les 48 tests Vitest.
