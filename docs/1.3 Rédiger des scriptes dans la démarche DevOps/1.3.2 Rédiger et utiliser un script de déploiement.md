# 1.3.2 Rédiger et utiliser un script de déploiement

## En bref

Ce chapitre décrit le script **`scripts/deploy-nas.sh`**, qui prépare et livre Hublot vers un NAS Synology : installation des dépendances, contrôles qualité (lint + 48 tests Vitest), build de production, puis copie locale ou synchronisation SSH. Il complète la CD Netlify pour un usage en réseau interne DIRM, sans exécuter `npm ci` sur le NAS.

---

## Objectif pédagogique

**Rédiger et utiliser un script de déploiement** : enchaînement d'étapes, variables d'environnement, gestion d'erreurs (`set -euo pipefail`), sorties vérifiables et documentation d'usage pour un opérateur.

---

## Contexte — projet Hublot

La production publique est sur **Netlify** (`https://dirmhublot.netlify.app`). Certaines utilisations (réunion direction, réseau fermé) exigent une instance **locale** sur Synology Container Manager. Le script `deploy-nas.sh` garantit que seule une version ayant passé les mêmes contrôles que la CI (`ci.yml`) est copiée sur le NAS : login, filtres région/service et graphiques ETP doivent fonctionner comme en prod.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Script de déploiement** | Fichier exécutable qui produit les artefacts et les place sur la cible. |
| **Rsync** | Synchronisation incrémentale des fichiers vers le NAS via SSH. |
| **Build statique** | Sortie Vite dans `build/` (HTML, JS, assets). |
| **Gate qualité** | Étapes bloquantes avant copie (lint, tests). |

---

## Ce qui a été mis en place

Le fichier `scripts/deploy-nas.sh` (Bash, ~50 lignes) réalise :

1. `npm ci` — dépendances figées (`package-lock.json`).
2. `npm run lint` — ESLint.
3. `npm run test:run` — **48 tests** Vitest.
4. `npm run build` — compilation production.
5. Vérification de `build/index.html`.
6. Miroir `build/` → `dist/` (certains `docker-compose` montent `dist/`).
7. Mode par défaut : message pour copie manuelle du projet sur le NAS.
8. Mode `--rsync` : envoi vers `NAS_USER@NAS_HOST:NAS_PATH` si les trois variables sont définies.

Fichiers Docker associés : `docker-compose.yml` (Nginx + volume statique, port **8080**), `nginx.conf`, variante `docker-compose.prod.yml` pour build sur NAS (non recommandée si Container Manager bloque sur `npm ci`).

---

## Pourquoi ces choix

**Intégrer lint et tests dans le script** aligne le déploiement NAS sur la CI : un opérateur ne peut pas publier un build cassé. **Build sur le poste de dev** évite les échecs Docker sur Synology (mémoire, réseau npm). **Rsync optionnel** sépare la préparation (toujours locale) de la publication (automatisée en CI via `cd-nas.yml` avec secrets). Nous n'avons pas mis le mot de passe dans le script : SSH par clé ou secrets GitHub uniquement.

---

## Comment ça fonctionne

### Étape 1 — Préparation locale (sans NAS)

```bash
cd /chemin/vers/Hublot
chmod +x scripts/deploy-nas.sh
./scripts/deploy-nas.sh
```

Le script s'arrête à la première erreur. En cas de succès, les dossiers `build/` et `dist/` contiennent la SPA prête à servir.

### Étape 2 — Copie manuelle sur le NAS

1. DSM → **File Station** → créer par ex. `/volume1/docker/statdirm`.
2. Copier le projet (incluant `build/`, `docker-compose.yml`, `nginx.conf`).
3. **Container Manager** → **Projet** → créer `statdirm` → compose `docker-compose.yml` → démarrer.
4. Accès : `http://IP_DU_NAS:8080` — vérifier login et chargement des données (`/data/agents.json`).

### Étape 3 — Rsync automatisé (optionnel)

```bash
NAS_HOST=192.168.1.10 \
NAS_USER=admin \
NAS_PATH=/volume1/docker/statdirm \
./scripts/deploy-nas.sh --rsync
```

Le script envoie `build/` vers `${NAS_PATH}/build/` et copie `docker-compose.yml` + `nginx.conf` à la racine du projet NAS. Sur le NAS : redémarrer le projet Container Manager.

### Comportement en cas d'échec

| Étape en échec | Cause fréquente | Action |
|----------------|-----------------|--------|
| `npm run test:run` | Régression métier ou sécurité | Corriger le code, relancer |
| `npm run build` | Erreur TypeScript / Vite | Corriger, relancer |
| rsync | SSH ou chemin NAS | Vérifier clés, `NAS_PATH`, pare-feu |

---

## Quand

| Situation | Commande |
|-----------|----------|
| Première install NAS | `./scripts/deploy-nas.sh` puis copie + compose |
| Mise à jour après merge `main` | Rebuild + rsync ou remplacement `build/` |
| Avant démo interne | Script complet + test navigateur |
| Pipeline `cd-nas.yml` | Même script avec secrets CI |

---

## Preuves et démonstration

```bash
./scripts/deploy-nas.sh
# Attendu en fin de log :
# ==> Artefacts prêts : build/ et dist/

npm run test:run
# 48 passed

curl -s -o /dev/null -w "%{http_code}" http://IP_NAS:8080/
# 200 sur la page d'accueil après démarrage du conteneur
```

Checklist opérationnelle :

- Conteneur **Running** dans Container Manager.
- `build/index.html` présent sur le NAS.
- Refresh sur une route React (SPA → `index.html` via `nginx.conf`).
- Données : fichier `public/data/agents.json` déployé ou volume à jour.

Référence racine (copie courte) : `DEPLOY_SYNOLOGY_LOCAL.md`.

---

## Synthèse

`deploy-nas.sh` formalise le déploiement interne de Hublot : mêmes garde-fous que la CI, artefacts `build/`/`dist/`, publication manuelle ou rsync vers le Synology.
