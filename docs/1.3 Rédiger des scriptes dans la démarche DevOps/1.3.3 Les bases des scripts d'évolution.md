# 1.3.3 Les bases des scripts d'évolution

## En bref

Les **scripts d'évolution** mettent à jour les données RH de Hublot à partir des exports Excel RenoiRH (feuille ETPT), sans modifier le code React à chaque mouvement d'effectifs. Nous avons défini une chaîne traçable : conversion Python, contrôles de cohérence, publication optionnelle vers Neon. Le point d'entrée standard est `scripts/run-evolution-pipeline.sh`, appuyé sur `convert_suivi_etpt_to_json.py`.

---

## Objectif pédagogique

**Comprendre les bases des scripts d'évolution de données** : séparer code applicatif et données, garantir traçabilité, validations avant publication, modes dry-run et production.

---

## Contexte — projet Hublot

Les tableaux de bord (filtres **région** / **service**, répartitions ETP, parité, pyramide des âges) consomment `public/data/agents.json` au runtime (`/data/agents.json`). La source métier est l'export **« Suivi des emplois en ETPT_RPROG »** déposé dans `trdata/`. Sans script d'évolution, chaque mise à jour imposerait une manipulation manuelle du JSON (erreurs d'IDs, services vides, données obsolètes sur `https://dirmhublot.netlify.app`).

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Script d'évolution** | Automatisation qui transforme une source (Excel) en artefact versionné (JSON). |
| **Dry-run** | Exécution sans effet de publication distant (pas de `--push-neon`). |
| **RenoiRH / ETPT** | Export ministériel des emplois en équivalent temps plein. |
| **Matricule** | Identifiant SIRH ; base de déduplication (une ligne par agent). |
| **Pipeline** | Enchaînement conversion + contrôles + empreinte (+ push optionnel). |

---

## Ce qui a été mis en place

| Composant | Fichier | Rôle |
|-----------|---------|------|
| Orchestrateur | `scripts/run-evolution-pipeline.sh` | Enchaîne conversion, contrôles Python inline, SHA256 |
| Convertisseur | `scripts/convert_suivi_etpt_to_json.py` | Excel « Données annuelles » → JSON StatDirm |
| Sorties | `src/data/agents.json`, `public/data/agents.json` | Build + servage HTTP |
| Legacy | `scripts/convert_excel_to_json.py` | Ancien format Interface_Effectifs (référence) |
| Diagnostic | `scripts/analyze_excel.py` | Structure des colonnes Excel |
| Application | `src/services/dataService.ts`, `src/hooks/useAgentsData.ts` | Chargement et agrégations |

Le modèle cible des champs est documenté dans [1.3.3.1](./1.3.3.1%20Mod%C3%A8le%20de%20donn%C3%A9es%20cible.md). La rédaction détaillée du pipeline : [1.3.4](./1.3.4%20R%C3%A9diger%20des%20scripts%20d%27%C3%A9volution.md).

---

## Pourquoi ces choix

**Python + pandas** pour la conversion : le fichier Excel est volumineux, multi-lignes par matricule (observations mensuelles) ; le script réduit à un agent par matricule et déduit genre/naissance depuis le NIR quand les colonnes manquent. **Double écriture** `src/data` et `public/data` : Vite sert les données en dev et Netlify les publie sans étape oubliée. **Orchestrateur Bash** : un seul point d'entrée pour l'équipe RH/DevOps, logs par étape, `--push-neon` explicite pour éviter une publication accidentelle. Le convertisseur historique reste pour compatibilité mais n'est plus le chemin nominal.

---

## Comment ça fonctionne

### Prérequis

```bash
pip3 install -r scripts/requirements.txt
npm ci   # si push Neon ou tests applicatifs ensuite
```

### Lancement standard (dry-run)

```bash
bash scripts/run-evolution-pipeline.sh \
  --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx"
```

Déroulé :

1. **Conversion** — `python3 scripts/convert_suivi_etpt_to_json.py` lit la feuille `Données annuelles` (en-tête ligne 5), mappe colonnes RenoiRH (NIR, matricule, région UO, programme/action, ETPT…).
2. **Contrôles** — agents non vides, IDs uniques, au moins un actif, aucun service vide.
3. **Empreinte** — SHA256 de `public/data/agents.json` pour traçabilité documentée.
4. **Neon** — ignoré sauf si `--push-neon` (voir [1.3.4.1](./1.3.4.1%20Publier%20et%20v%C3%A9rifier%20les%20donn%C3%A9es%20sur%20Netlify.md)).

### Côté application

Au démarrage (`npm run dev`), l'app charge `/data/agents.json`. Les **48 tests Vitest** valident filtres et calculs (`dataService.test.ts`, `dataCalculations.test.ts`) après chaque évolution de données ou de code.

---

## Quand

| Fréquence / événement | Action |
|----------------------|--------|
| Réception export mensuel RenoiRH | Pipeline `--file` puis revue compteurs |
| Avant `git push` vers `main` | Dry-run + `npm run test:run` |
| Publication Neon | Pipeline avec `--push-neon` après validation métier |
| Après évolution | Commit `public/data/agents.json` (et `src/data` si suivi Git) |

---

## Preuves et démonstration

```bash
bash scripts/run-evolution-pipeline.sh --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx"
# Logs attendus : Agents totaux / Agents actifs / Contrôles : OK
# SHA256 agents.json: <empreinte>

npm run test:run
# 48 passed — non-régression métier après nouvelles données
```

Vérification manuelle rapide : ouvrir Hublot, filtre **DIRM Méditerranée** (ou région cible), contrôler effectifs et graphiques missions.

---

## Synthèse

Les scripts d'évolution de Hublot transforment l'Excel ETPT en JSON validé, via `run-evolution-pipeline.sh` et `convert_suivi_etpt_to_json.py`, avant toute mise en ligne Netlify ou NAS.
