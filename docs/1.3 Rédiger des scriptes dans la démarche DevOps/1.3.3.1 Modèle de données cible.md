# 1.3.3.1 Modèle de données cible

## En bref

Ce chapitre décrit le **modèle de données cible** de Hublot : structure JSON `agents.json`, interface TypeScript `Agent` dans `src/types/data.ts`, champs issus de l'export ETPT et agrégats calculés par l'application (ETP, répartitions, filtres PASA). Il sert de contrat entre les scripts d'évolution et le front React.

---

## Objectif pédagogique

**Définir un modèle de données cible** pour une application métier : typage, champs obligatoires, cohérence avec la source Excel et avec les écrans (tableaux, graphiques, carte).

---

## Contexte — projet Hublot

Les utilisateurs DIRM consultent effectifs, missions, régions et indicateurs RH via des filtres globaux (région, service, statut, segments PASA). Toutes ces vues lisent le même fichier **`public/data/agents.json`** (URL `/data/agents.json`). Le convertisseur `convert_suivi_etpt_to_json.py` doit produire exactement ce schéma pour que `dataService.ts` et les **48 tests Vitest** restent verts.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Agent** | Enregistrement nominatif (une personne après déduplication matricule). |
| **ETP** | Équivalent temps plein (0–1 ou plus selon répartition). |
| **PASA** | Segmentation politique / programme (codes et libellés). |
| **Agrégat** | Statistique calculée à la volée (âge moyen, taux de remplissage). |
| **StatDirmData** | Enveloppe JSON `{ "agents": [ ... ], "metadonnees": ... }`. |

---

## Ce qui a été mis en place

### Fichier de référence TypeScript

Le contrat applicatif est dans `src/types/data.ts` : interface **`Agent`** (identité, affectation, temps de travail, métadonnées) et types dérivés (`OverviewStats`, répartitions âge/genre/statut, capacités missions/régions).

Champs notables ajoutés pour l'export RenoiRH :

- `uniteService`, `missionCode` — granularité opérationnelle.
- `pasaCode`, `pasaLibelle`, `pasaSegment`, `pasaSousSegment` — filtres politiques publiques.
- `corps`, `fonctionExercee`, `fonctionCategorie` — référentiels grade/poste.
- `tempsTravailRenseigne` — traçabilité colonne source.

### Enveloppe JSON

```json
{
  "agents": [ { "id": "...", "nom": "...", ... } ],
  "metadonnees": {
    "dateExport": "YYYY-MM-DD",
    "source": "Suivi ETPT_RPROG",
    "version": "1.0"
  }
}
```

Les fichiers générés sont écrits en parallèle dans `src/data/agents.json` et `public/data/agents.json`.

### Champs obligatoires pour le pipeline

Le script `run-evolution-pipeline.sh` refuse une publication si :

- la liste `agents` est vide ;
- des **IDs** sont dupliqués ;
- aucun agent `actif: true` ;
- un agent n'a pas de `service` renseigné.

---

## Pourquoi ces choix

**TypeScript centralisé** évite la dérive entre script Python et React : les tests unitaires compilent les mêmes attentes. **Région en `string` élargi** (pas seulement Marseille/Nice…) car l'Excel contient toutes les DIRM ; l'UI filtre sur la Méditerranée. **Dérivation NIR** (genre, date de naissance) compense l'absence de colonnes dédiées dans l'ETPT. Nous n'avons pas imposé une base SQL en production Netlify par défaut : le JSON statique reste le mode simple ; Neon est optionnel ([1.3.4.1](./1.3.4.1%20Publier%20et%20v%C3%A9rifier%20les%20donn%C3%A9es%20sur%20Netlify.md)).

## Comment ça fonctionne

### Agent — champs principaux

| Groupe | Champs | Usage Hublot |
|--------|--------|--------------|
| Identité | `id`, `nom`, `prenom`, `dateNaissance`, `genre` | Listes, masquage RH, âge |
| Contrat | `statut`, `contratType`, `tempsPartielPourcentage`, `etp` | Donuts statut, ETP |
| Affectation | `region`, `service`, `mission`, `metier`, `poste` | Filtres, graphiques mission |
| Hiérarchie | `niveauResponsabilite` | Encadrement, ratio |
| PASA | `pasaCode`, `pasaLibelle`, … | Filtres politiques |
| État | `actif`, `enConges`, `enFormation`, `enArretMaladie` | Effectifs présents |
| Dates | `dateEmbauche`, `dateMaj` | Fraîcheur des données |

### Agrégats (calculés, non stockés dans le JSON source)

`src/utils/dataCalculations.ts` et `dataService.ts` produisent :

- tranches d'âge, parité H/F, répartition par statut ;
- statistiques vue d'ensemble (postes pourvus/vacants, tension RH) ;
- capacités missions/régions lorsque les métadonnées ou règles métier le permettent.

Exemple de flux :

```
Excel ETPT → convert_suivi_etpt_to_json.py → agents.json
  → fetch /data/agents.json → dataService → hooks → composants (OverviewCards, RegionMap, …)
```

### Mapping Excel → JSON (extrait)

| Colonne Excel (RenoiRH) | Champ JSON |
|-------------------------|------------|
| Etat Civil : Matricule SIRH | `id` |
| Etat Civil : NIR | dérivation `genre`, `dateNaissance` |
| Affect. Opé.Reg UO : Libellé Long | `region` |
| Niveau 08 Opé. : Libellé Court | `service` |
| ETPT RH : Action / Programme | `mission`, `missionCode` |
| ETPT RH | `etp` |

Le détail des colonnes `COL` est en tête de `scripts/convert_suivi_etpt_to_json.py`.

---

## Quand

| Événement | Impact sur le modèle |
|-----------|---------------------|
| Nouvelle colonne RenoiRH | Mettre à jour `COL` + `Agent` + tests |
| Nouvel indicateur UI | Étendre types + calculs + tests |
| Revue de conformité | Montrer `src/types/data.ts` + extrait JSON |

## Preuves et démonstration

```bash
# Générer les données conformes au modèle
bash scripts/run-evolution-pipeline.sh --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx"

# Vérifier structure minimale
python3 -c "import json; d=json.load(open('public/data/agents.json')); a=d['agents'][0]; print(sorted(a.keys())[:12])"

npm run test:run
# dataService.test.ts + dataCalculations.test.ts couvrent filtres et calculs
```

Contrôle manuel : dans l'app, filtrer une région et un service — les compteurs doivent correspondre à un sous-ensemble cohérent du JSON.

---

## Synthèse

Le modèle cible Hublot est l'interface `Agent` et l'enveloppe `agents.json`, alimentés par le convertisseur ETPT et validés par le pipeline d'évolution et les 48 tests Vitest.
