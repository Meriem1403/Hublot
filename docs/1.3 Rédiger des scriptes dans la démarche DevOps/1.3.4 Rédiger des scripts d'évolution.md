# 1.3.4 Rédiger des scripts d'évolution

## En bref

Ce chapitre détaille la **rédaction** et l'**exécution** des scripts d'évolution de Hublot : orchestrateur Bash `run-evolution-pipeline.sh`, convertisseur Python `convert_suivi_etpt_to_json.py`, contrôles intégrés et option `--push-neon`. L'objectif est un script lisible, paramétrable et sûr avant toute publication des données RH.

---

## Objectif pédagogique

**Rédiger des scripts d'évolution de données** : arguments CLI, gestion d'erreurs, logs, validations métier, séparation conversion / publication.

---

## Contexte — projet Hublot

Chaque mois, l'administration transmet un classeur **Suivi des emplois en ETPT_RPROG**. Le script doit transformer des milliers de lignes (plusieurs mois par agent) en un JSON unique exploitable par les graphiques (missions, régions, ETP). Sans orchestrateur, on risque d'oublier les contrôles d'IDs ou de pousser vers Neon une version incomplète, visible ensuite sur `https://dirmhublot.netlify.app`.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Orchestrateur** | Script qui appelle les sous-scripts dans un ordre fixe. |
| **Argument `--file`** | Chemin vers le fichier Excel source (obligatoire). |
| **Bloc Python inline** | Contrôles dans le pipeline sans fichier séparé. |
| **`--push-neon`** | Déclenche `npm run push-agents-to-neon` après validation. |

---

## Ce qui a été mis en place

### `run-evolution-pipeline.sh`

- Options : `--file`, `--push-neon`, `--help`.
- `set -euo pipefail` — arrêt immédiat si une étape échoue.
- Mesure du temps par étape (`step_start` / `step_end`).
- Étapes : conversion → contrôles JSON → SHA256 → push Neon optionnel.

### `convert_suivi_etpt_to_json.py`

- Lecture feuille **`Données annuelles`**, en-tête ligne 5 (`HEADER_ROW = 4`).
- Dictionnaire **`COL`** : libellés Excel exacts RenoiRH.
- Réduction **un agent par matricule** (dernière observation retenue).
- Dérivation **genre / dateNaissance** depuis le NIR si absentes.
- Écriture **`src/data/agents.json`** et **`public/data/agents.json`**.

### Scripts npm liés

| Commande | Rôle |
|----------|------|
| `npm run copy-data-for-netlify` | Copie `src/data` → `public/data` si besoin |
| `npm run push-agents-to-neon` | Publication base Neon (option 2 Netlify) |

Index opérationnel : `scripts/README.md`.

---

## Pourquoi ces choix

**Bash pour l'orchestration** : l'équipe DevOps lance une seule commande ; Python reste dédié au traitement tabulaire. **Contrôles dans le pipeline** plutôt qu'un second script : impossible de « sauter » la validation en appelant seulement le convertisseur. **`--push-neon` explicite** : la publication base distante est une décision consciente après validation métier. Messages d'erreur en français dans les `SystemExit` Python pour faciliter le diagnostic côté RH.

---

## Comment ça fonctionne

### Aide et syntaxe

```bash
bash scripts/run-evolution-pipeline.sh --help
```

### Exécution nominale

```bash
bash scripts/run-evolution-pipeline.sh \
  --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx"
```

1. Vérifie que le fichier existe.
2. Lance `python3 scripts/convert_suivi_etpt_to_json.py "$EXCEL_FILE"`.
3. Exécute le bloc de contrôle (agents, IDs uniques, actifs, services).
4. Affiche SHA256 de `public/data/agents.json`.
5. Indique que le push Neon est ignoré (dry-run).

### Publication Neon

```bash
bash scripts/run-evolution-pipeline.sh \
  --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx" \
  --push-neon
```

Prérequis : `.env` avec `NETLIFY_DATABASE_URL` (copiée depuis Netlify → Environment variables).

### Convertisseur seul (debug)

```bash
python3 scripts/convert_suivi_etpt_to_json.py "trdata/mon_export.xlsx"
```

Utile pour analyser une erreur de colonne avant de relancer le pipeline complet.

### Après évolution

```bash
npm run test:run          # 48 tests
npm run copy-data-for-netlify   # si seul src/data a changé
git add public/data/agents.json src/data/agents.json
git commit -m "Données RH : export ETPT <mois>"
git push
```

La CI (`ci.yml`) rejoue lint, tests, build et E2E.

## Quand

| Qui / quand | Script |
|-------------|--------|
| Référent données, réception Excel | `run-evolution-pipeline.sh --file` |
| Validation OK, prod Netlify JSON | commit + push |
| Prod Neon activée | `--push-neon` puis push code si besoin |
| Debug colonnes | `analyze_excel.py` ou convertisseur seul |

## Preuves et démonstration

Sortie attendue (extrait) :

```
==> Conversion Excel -> JSON
...
==> Contrôles de cohérence JSON
Agents totaux : <n>
Agents actifs : <m>
Contrôles : OK
==> Empreinte de version des données
SHA256 agents.json: <hash>
```

```bash
npm run test:run
# 48 passed

grep -c '"id"' public/data/agents.json
# cohérent avec le log « Agents totaux »
```

---

## Synthèse

Les scripts d'évolution de Hublot sont écrits pour être sûrs par défaut : `convert_suivi_etpt_to_json.py` produit le JSON, `run-evolution-pipeline.sh` valide et trace, `--push-neon` ne s'exécute qu'à la demande.
