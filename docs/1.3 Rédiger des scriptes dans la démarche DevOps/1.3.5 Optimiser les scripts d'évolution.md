# 1.3.5 Optimiser les scripts d'évolution

## En bref

Ce chapitre présente les **optimisations** apportées aux scripts d'évolution de Hublot : mesure du temps par étape, mode dry-run par défaut, point de publication explicite (`--push-neon`), contrôles automatiques et empreinte SHA256. L'objectif est de réduire les erreurs humaines et d'accélérer le diagnostic quand un export Excel change de structure.

---

## Objectif pédagogique

**Optimiser des scripts d'évolution** : performance mesurable, sécurité opérationnelle (dry-run / prod), validations anticipées, traçabilité des versions de données.

---

## Contexte — projet Hublot

Un export ETPT incorrect (colonnes renommées, matricules dupliqués) peut casser les graphiques en production ou faire échouer les **48 tests Vitest** en CI. Les optimisations du pipeline protègent la DIRM avant le `git push` vers Netlify et évitent un push Neon avec des données incohérentes.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Timing par étape** | Durée affichée en millisecondes entre `step_start` et `step_end`. |
| **Dry-run** | Pipeline sans `npm run push-agents-to-neon`. |
| **Empreinte SHA256** | Hash du fichier `agents.json` pour comparer deux exports. |
| **Fail-fast** | `set -euo pipefail` — arrêt dès la première erreur. |

---

## Ce qui a été mis en place

| Optimisation | Où | Bénéfice |
|--------------|-----|----------|
| Chronométrage | `run-evolution-pipeline.sh` | Repérer une conversion lente ou bloquante |
| Dry-run par défaut | Pas de `--push-neon` | Pas de publication DB accidentelle |
| Publication explicite | Flag `--push-neon` | Séparation validation / mise en prod données |
| Contrôles structurels | Bloc Python inline | IDs, actifs, services — avant commit |
| Empreinte SHA256 | `shasum -a 256` sur `public/data/agents.json` | Preuve lecteur (« quelle version est en prod ? ») |
| Déduplication matricule | `convert_suivi_etpt_to_json.py` | Fichier JSON plus petit, chargement UI plus rapide |
| Double sortie contrôlée | `src/data` + `public/data` | Pas d'écart build Netlify / dev |

Pistes non prioritaires (si volume ×10) : cache pandas intermédiaire, parallélisation par feuille — non nécessaires au périmètre actuel DIRM.

---

## Pourquoi ces choix

**Mesurer avant d'optimiser le code Python** : le goulot est souvent la taille Excel, pas le script ; le timing oriente vers un fichier source trop lourd ou un disque lent. **Dry-run** coûte peu et évite un incident Neon. **SHA256** est plus fiable qu'un horodatage de fichier pour prouver qu'un deploy contient bien l'export du 2 juin. Nous avons évité une UI d'administration dédiée : un script CLI documenté suffit au référent données.

---

## Comment ça fonctionne

### Lire les timings

```bash
bash scripts/run-evolution-pipeline.sh --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx"
```

Exemple de sortie :

```
==> Conversion Excel -> JSON
...
terminé en 8420 ms
==> Contrôles de cohérence JSON
...
terminé en 120 ms
```

Si la conversion dépasse systématiquement un seuil interne, vérifier taille du xlsx, antivirus, ou exécuter depuis un SSD local.

### Comparer deux versions de données

```bash
# Run 1
bash scripts/run-evolution-pipeline.sh --file "trdata/export_a.xlsx"
# noter SHA256

# Run 2 après correction Excel
bash scripts/run-evolution-pipeline.sh --file "trdata/export_b.xlsx"
# hashes différents ⇒ données différentes commitées
```

### Enchaînement optimisé avant prod

1. Pipeline dry-run + compteurs agents.
2. `npm run test:run` (48 tests).
3. Revue métier (filtre Méditerranée dans l'app locale).
4. Commit JSON ou `--push-neon`.
5. `git push` → CI → Netlify.

### En cas d'échec de contrôle

| Message | Cause probable | Correction |
|---------|----------------|------------|
| IDs dupliqués | Matricule en double après fusion | Corriger logique ou source Excel |
| Aucun agent actif | Filtre trop agressif | Revoir règles `actif` dans le convertisseur |
| Agents sans service | Colonne service vide | Compléter Excel ou mapping Niveau 08 |

---

## Quand

| Situation | Utiliser |
|-----------|----------|
| Premier export du mois | Timing + SHA256 archivés dans le ticket / mail équipe |
| Doute « prod ≠ fichier local » | Comparer SHA256 local vs extrait prod |
| Incident après push Neon | Relancer sans `--push-neon`, corriger, puis push ciblé |
| Revue performance | Logs `terminé en … ms` sur 3 runs consécutifs |

---

## Preuves et démonstration

```bash
bash scripts/run-evolution-pipeline.sh --file "trdata/Suivi_des_emplois_en_ETPT_RPROG (23).xlsx" 2>&1 | tee /tmp/pipeline.log
grep -E '^(==>|SHA256|Agents|Contrôles)' /tmp/pipeline.log

npm run test:run
# 48 passed — garde-fou après optimisation données
```

## Synthèse

Les scripts d'évolution Hublot sont optimisés pour la sûreté et la traçabilité : temps mesuré, dry-run par défaut, validations et empreinte SHA256 avant toute publication Netlify ou Neon.
