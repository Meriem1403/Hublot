# 1.3.6 Ecrire un script YAML d'Intégration Continue

## En bref

Ce chapitre explique comment le workflow **CI** de Hublot est **écrit en YAML** (`.github/workflows/ci.yml`) : déclencheurs, jobs parallèles, dépendances `needs`, artefact de build et enchaînement E2E. La CI exécute lint, **48 tests** Vitest, audit npm et build avant toute CD Netlify ou NAS.

---

## Objectif pédagogique

**Écrire un script YAML d'intégration continue** : structure GitHub Actions, jobs, steps, cache npm, concurrence, séparation CI (qualité) et CD (déploiement).

---

## Contexte — projet Hublot

Chaque contribution sur `main` ou `staging` doit garantir que l'application compile, que les filtres région/service restent corrects et que le login E2E fonctionne. Le fichier `ci.yml` est la source de vérité exécutée sur `ubuntu-latest` avec Node 20 — même environnement cible que Netlify et que `scripts/deploy-nas.sh` (qui rejoue lint + tests en local).

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Workflow** | Fichier YAML dans `.github/workflows/`. |
| **Job** | Bloc parallélisable (ex. `lint`, `unit-tests`). |
| **Step** | Commande ou action (`uses: actions/checkout@v4`). |
| **`needs`** | Dépendance entre jobs (E2E après `build`). |
| **Concurrency** | Annule les runs obsolètes sur la même branche. |

---

## Ce qui a été mis en place

Fichier **`.github/workflows/ci.yml`** (commentaire d'en-tête : CI sans déploiement ; CD = Netlify + `deploy-nas.sh`).

| Job | Commande clé | Rôle |
|-----|--------------|------|
| `lint` | `npm run lint` | Qualité code ESLint |
| `unit-tests` | `npm run test:run` | **48 tests** Vitest |
| `audit` | `npm run audit:prod` | Vulnérabilités dépendances prod |
| `build` | `npm run build` + vérif `build/index.html` | Artefact Vite |
| `e2e` | `npm run test:e2e` (Playwright) | Parcours login / dashboard |

Paramètres transverses :

- **on** : `push` et `pull_request` sur `main`, `staging` ; `workflow_dispatch`.
- **concurrency** : `ci-${{ github.ref }}`, `cancel-in-progress: true`.
- **cache** : `cache: npm` dans `setup-node@v4`.
- **artefact** : upload `build/` (`retention-days: 7`).

CD séparée : `cd-netlify.yml`, `cd-nas.yml` (voir [1.1.5](../1.1%20Les%20bases%20de%20la%20d%C3%A9marche%20DevOps/1.1.5%20La%20mise%20en%20place%20de%20la%20livraison%20ou%20d%C3%A9ploiement%20continu%20(CD).md)).

---

## Pourquoi ces choix

**Jobs lint / tests / audit en parallèle** réduisent le temps de feedback ; seul `build` attend les trois (`needs: [lint, unit-tests, audit]`). **E2E après build** garantit un bundle proche de la prod (`npm run build:e2e`). **Pas de déploiement dans `ci.yml`** : principe de moindre privilège — les secrets Netlify/NAS ne sont pas exposés au job de test. **Concurrency avec annulation** évite de payer dix runs sur dix pushes rapides. Introduction YAML générale : [1.1.6](../1.1%20Les%20bases%20de%20la%20d%C3%A9marche%20DevOps/1.1.6%20Introduction%20au%20YAML.md).

## Comment ça fonctionne

### Structure YAML (extrait commenté)

```yaml
name: CI
on:
  push:
    branches: [main, staging]
  pull_request:
    branches: [main, staging]

jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - run: npm run test:run

  build:
    needs: [lint, unit-tests, audit]
    # ...
```

### Déroulé d'un push

1. GitHub reçoit le commit sur `Meriem1403/Hublot`.
2. Trois jobs démarrent en parallèle (lint, tests, audit).
3. Si les trois sont verts, `build` compile et upload l'artefact.
4. `e2e` installe Chromium, build E2E, exécute Playwright avec `CI: true`.
5. Netlify (required checks) peut déployer si branche `main` et politique activée.

### Alignement local

```bash
npm ci
npm run lint
npm run test:run
npm run audit:prod
npm run build
npm run test:e2e   # optionnel, plus long
```

Identique à `scripts/check-test-environment.sh` pour un poste développeur.

## Quand

| Événement | Comportement CI |
|-----------|-----------------|
| Push / PR `main` ou `staging` | Workflow complet |
| Push documentation seule | CI tourne quand même (pas de path filter) |
| Déploiement NAS manuel | Recommandé : même commandes que CI via `deploy-nas.sh` |
| Déclenchement manuel | Actions → CI → Run workflow |

## Preuves et démonstration

- Onglet Actions : workflow **CI** vert sur le SHA de `main`.
- Job **Tests unitaires** : log `48 passed`.
- Job **Build production** : présence artefact `build-<sha>`.
- Job **Tests E2E** : scénarios Playwright passés.

```bash
# Local — reproduire la gate
npm run test:run
# Tests  48 passed (4 files)
```

Fichier source : `.github/workflows/ci.yml` à la racine du dépôt.

---

## Synthèse

Le YAML `ci.yml` formalise l'intégration continue de Hublot : parallélisme des contrôles, build artefact, E2E en aval, sans mélanger le déploiement.
