# 1.3.7 Automatiser les tests en DevOps

## En bref

Ce chapitre décrit **l'automatisation des tests** de Hublot dans la démarche DevOps : **48 tests** unitaires Vitest, tests de sécurité, audit npm, build et E2E Playwright, tous déclenchés par `.github/workflows/ci.yml` à chaque push ou pull request. Les scripts `deploy-nas.sh` et le pipeline d'évolution s'appuient sur la même commande `npm run test:run` pour éviter de livrer une régression.

---

## Objectif pédagogique

**Automatiser les tests en DevOps** : intégrer la batterie de tests dans la CI, lier les résultats au déploiement, documenter commandes et fichiers sources pour la traçabilité et l'auditabilité.

---

## Contexte — projet Hublot

Les tableaux de bord manipulent des données RH sensibles (filtres, masquage, calculs ETP). Une erreur de filtre « région » ou de calcul d'âge fausse les décisions de direction. L'automatisation garantit que chaque modification de code **ou** de `agents.json` est vérifiée avant d'atteindre `https://dirmhublot.netlify.app`.

---

## Définitions

| Terme | Définition |
|-------|------------|
| **Vitest** | Framework de tests unitaires (compatible Vite). |
| **`test:run`** | `vitest run` — exécution unique non watch. |
| **Pyramide de tests** | Beaucoup d'unitaires, peu d'E2E ciblés. |
| **Required check** | Job CI obligatoire avant merge / deploy. |
| **E2E** | Tests bout en bout Playwright (navigateur). |

## Ce qui a été mis en place

### Batterie unitaire (48 tests)

| Fichier | Tests | Couverture |
|---------|-------|------------|
| `src/services/dataService.test.ts` | 12 | Filtres, chargement, normalisation |
| `src/utils/dataCalculations.test.ts` | 20 | Âge, ETP, répartitions, stats service |
| `src/utils/security.test.ts` | 15 | Sanitization, session, masquage RH |
| `src/config/environment.test.ts` | 1 | Libellé environnement DEV / prod |

Commande : `npm run test:run`.

### Autres contrôles automatisés

| Outil | Commande | Où |
|-------|----------|-----|
| ESLint | `npm run lint` | Job `lint` dans `ci.yml` |
| Audit prod | `npm run audit:prod` | Job `audit` |
| Build | `npm run build` | Job `build` |
| Playwright | `npm run test:e2e` | Job `e2e` (après build) |

### Intégration dans les scripts DevOps

- **`ci.yml`** — exécute toute la chaîne sur GitHub Actions.
- **`deploy-nas.sh`** — `npm run test:run` avant `npm run build`.
- **Évolution données** — après `run-evolution-pipeline.sh`, `npm run test:run` recommandé avant commit.

Plan et scénarios manuels complémentaires : [1.2.5](../1.2%20Pr%C3%A9parer%20le%20d%C3%A9ploiement%20d%27une%20application/1.2.5%20Planifier%20efficacement%20les%20tests.md), [1.2.8](../1.2%20Pr%C3%A9parer%20le%20d%C3%A9ploiement%20d%27une%20application/1.2.8%20Proc%C3%A9dure%20d%27ex%C3%A9cution%20des%20tests%20(%C3%A9preuve).md).

## Pourquoi ces choix

**Unitaires nombreux** : rapides (< quelques secondes), stables, couvrent la logique métier Excel→JSON→UI sans navigateur. **E2E limités** (login, dashboard, health) : coût CI plus élevé, réservés aux parcours critiques. **Audit npm en CI** : bloque les vulnérabilités critical sur les dépendances de production. **Même commande partout** (`test:run`) : pas d'écart entre développeur, NAS et GitHub. Les tests manuels (responsive, filtres ST-F*) restent documentés en 1.2 en complément ; la gate automatique est la CI.

---

## Comment ça fonctionne

### Développeur — avant commit

```bash
npm run test:run
npm run lint
```

### CI — à chaque push / PR

1. Checkout du dépôt `Meriem1403/Hublot`.
2. `npm ci` avec cache.
3. Jobs parallèles puis `build` puis `e2e` (voir [1.3.6](./1.3.6%20Ecrire%20un%20script%20YAML%20d%E2%80%99Int%C3%A9gration%20Continue.md)).
4. Si échec : pas de merge recommandé ; Netlify ne reçoit pas un deploy sain si required checks activés.

### Après évolution des données

```bash
bash scripts/run-evolution-pipeline.sh --file "trdata/....xlsx"
npm run test:run
# Si échec : corriger convertisseur ou données source, pas de git push
```

### Poste de test complet

```bash
bash scripts/check-test-environment.sh
```

Reproduit lint, tests, audit et build:test pour coller à l'environnement TEST CI.

| Moment | Tests exécutés |
|--------|----------------|

| PR ouverte | CI sur la branche |
| Avant `deploy-nas.sh` | lint + 48 unitaires + build |
| Après nouveau `agents.json` | `test:run` local obligatoire |
| Validation Studi | CI verte + `test:run` local reproductible |

npm run test:run

```

Sur GitHub : workflow **CI** → job **Tests unitaires** → log vert.

| Preuve | Où la trouver |
|--------|----------------|
| 48 passed | Sortie `npm run test:run` ou log Actions |
| E2E | Job `e2e` dans `ci.yml` |
| Prod stable | `https://dirmhublot.netlify.app` + dernier SHA CI vert |
| Rapport d'exécution | [1.2.9](../1.2%20Pr%C3%A9parer%20le%20d%C3%A9ploiement%20d%27une%20application/1.2.9%20Rapport%20d%27ex%C3%A9cution%20des%20tests.md) |

# Sécurité (inclus dans les 48 via security.test.ts)
npm run test:run -- src/utils/security.test.ts
```

## Synthèse

Hublot automatise **48 tests** Vitest et la chaîne lint / audit / build / E2E dans `ci.yml`, avec la même gate dans `deploy-nas.sh` et après chaque évolution de données.
